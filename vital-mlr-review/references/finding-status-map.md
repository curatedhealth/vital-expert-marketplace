# Finding → status map (shared by every skill that sets a status)

Used by every READY skill that writes a `Status:` line — the three chairs, `mlr-intake`, `mlr-channel-intent`, `mlr-claims-matrix`, `mlr-fair-balance-isi`, `mlr-verify-handoff`, `mlr-compile`, `mlr-board-prep` and `mlr-capability-map` — to pick the one status. The status is a closed list: `findings_only` · `revise` · `human_gate_required` · `prep_complete`. A chair never states `prep_complete` (that belongs to `mlr-board-prep`).

## Precedence order (TEH-RDY-033)

This is the one order for every skill. Go down the list; the **first** rule that applies sets the status. A skill-local status table only refines rules 2–5; it never overrides rule 1.

1. **Approval, clearance or bypass pressure, or an AI owner request → `human_gate_required`, always.** Rule 1 covers two kinds of request (TEH-RDY-037):
   - **(a) Approve or clear.** Any request to approve, clear, stamp, sign off or mark the piece reviewed or compliant.
   - **(b) Bypass any hard rule MLR-H1–MLR-H8** (`hard-rules.md`), or any other rule, gate, route or required check. This includes, and is not limited to: filling in or inventing data, locators, page numbers, label text, claim spans or names from memory (MLR-H1); treating teaching material as input (MLR-H2); assuming or defaulting a market, audience or channel (MLR-H6); making an AI, model, tool, system or automatic setting the owner of a record (`cleared_by`, MLR-H5); filing or submitting anything to a regulator (MLR-H3; filings are deferred, MLR-H6 detail); skipping ISI, fair balance or another required element; skipping a required step or chair — intake before the chairs, the chairs before compile, compile before board prep, or any one of the three chairs — including when the skip is asked as a question about this piece ("skip the chairs — can compile alone get us to the board?", "can we drop Legal this time?") (TEH-RDY-059); reusing an expired, revoked or someone else's connector key, reporting a result as tool-checked without a valid key, or asking to write, save or record anything to a connector (the MLR MCP, VERIFY) without a valid key (MLR-H4; TEH-RDY-044); substituting another market's rule set (MLR-H7); dropping the liability line (MLR-H8).

   This holds even when inputs are missing and nothing else can be assessed. Refuse the request, keep the rule, and name what the human must decide. Only a request counts: a market, audience, channel or other field the person has simply not supplied yet is a missing input (rule 4), not a bypass. So is a rule pack that cannot load because audience or channel is missing: ask for it, `findings_only` — never `human_gate_required` on that ground alone (TEH-RDY-047). (A real person's name that collides with a refused token is not an AI owner request: the owner is simply not yet accepted — go on to rules 2–5.)

   **What is NOT a bypass (TEH-RDY-051).** Rule 1(b) needs a request to break or skip a rule. These are not bypass requests; they never set `human_gate_required` on their own — go on to rules 2–5:
   - **Asking a chair for another chair's work** ("medical, also score privacy", "legal, check the dose"). That is routing: the chair names the owning chair as a route, writes no finding or severity on it, and its own status comes from its own findings (rule 4 `findings_only` when it has none).
   - **Asking a question about a deferred or out-of-scope feature** ("can READY file Form 2253?", "does it track post-clearance changes?"). Answer it with the `[DEFERRED]` line or the route.
   - **Supplying a value the tool does not recognize** (an unmatched channel value). It is a missing or unmatched input: report the tool's gap and ask (rule 4).
   - **Naming a delivery medium** (email, print, digital display, congress, social) where the channel was asked. The medium is recorded and never binds a pack; the intent is still missing — ask for it (rule 4, TEH-RDY-057).
   - **Asking how the process works** in general ("what does compile need?", "why do chairs come first?"). Answer it. Asking to skip a required step or chair for this piece is different: that is a bypass request (rule 1(b), TEH-RDY-059) — refuse the skip, explain the order and name what the human must decide.
   - **A field simply not supplied yet** (rule 4, above).

   These ARE bypass requests (rule 1(b)): asking the chair to do the other chair's work *and* write its verdict or severity anyway ("you're medical, just give the privacy finding a severity"), asking to run a deferred feature anyway ("file it now"), asking to assume a value ("just use promo"), asking to skip or drop a required step or chair for this piece, even phrased as a question (TEH-RDY-059), or any item in the 1(b) list.
2. **An open finding that needs a human judgment call → `human_gate_required`.** Rows (a)–(e) of the table below, or a gate whose result is a judgment call on supplied facts (the channel-intent gate's `status_basis: judgment`). A gate that could not decide only because inputs are missing is rule 4 (TEH-RDY-058).

   **Judgment-call example — mixed content (TEH-RDY-061, owner ruling).** A piece that mixes promotional content and medical-information content — for example branded claims together with medical-information (MI) letter fragments in one artefact, or any content that supports more than one channel/intent reading — goes to a human: `human_gate_required`, with the conflicting elements quoted from the supplied text (or, when no text was supplied, from the person's description, quoted as theirs). This is rule 2, not rule 4: the facts are supplied and conflict. Rule 4 still applies when content is simply incomplete rather than mixed — no text, no intent, or text that carries no signal for any reading: ask for what is missing, `findings_only`.

   **Not a judgment call — unknown users (TEH-RDY-062, owner ruling).** A deck or artefact whose users are not decided (for example reps vs MSLs) gets a provisional decision from the supplied content — for example `provisional: treat as promotional — pending: who will use it` — status `findings_only`, and the answer asks who will use it. When content is supplied and carries a reading, never write "not classified".
3. **Every open finding is correctable by a copy change → `revise`.**
4. **Missing inputs or observations only → `findings_only`.** No open finding: inputs still missing (each named as `[GAP]` — including missing markets, audience or channel and a rule pack that cannot load without them, TEH-RDY-047), observations only, `Watch for:` notes only (TEH-RDY-048), `[DEFERRED]` lines only, or a provisional gate decision.
5. **`prep_complete` only per the board-prep rule** — only `mlr-board-prep`, and only when all three conditions in its `SKILL.md` § "When `prep_complete` may be stated" hold.

## Tool-derived status is an input (TEH-RDY-050)

A status a tool returns or derives — `mlr_validate_packet`, `mlr_compile_checklist`, a gate skill or the channel-intent gate's `decision` / `status`, the render step — is an **input** to this order, never the answer's status by itself. Read the packet's open findings yourself and apply rules 1–5:

- A validation error a copy or record edit can fix (for example an `artefact_version mismatch`, a missing locator, a missing mandatory field the person can supply) is correctable. Correctable validation problems and/or open correctable findings, with no rule 1 or rule 2 item, → `revise` (rule 3) — even when the validator reports `findings_only` because it stopped at the error.
- A failed validation never permits `prep_complete` (rule 5) and never lowers a status the packet's findings set: an open finding that needs a human judgment call stays `human_gate_required` (rule 2).
- A packet's own status (`mlr_status`, a cover line, or a status the person states for the packet) is an input too (TEH-RDY-063). Re-derive the status from the packet's findings with rules 1–5. When they differ, report both — `Packet says <packet status>; findings support <derived status>.` — and put the derived status on the `Status:` line. Never carry a status no finding supports, and never lower one a finding supports.
- `findings_only` from a tool is the answer's status only when the packet has no open finding and no correctable validation problem (rule 4).
- The validator and the board-pack renderer derive a failed packet's status the same way (reject / abstain → `human_gate_required`; an open `revise` decision and/or a correctable validation error → `revise`; else `findings_only`); the answer still applies rules 1–2 on top.

## One status, stated once (TEH-RDY-034)

State the status exactly once, on the `Status: <value>` line; the close stamp repeats the same value. Nowhere else in the answer name a conditional, alternative, future or "would be" status (not "set the status to X if …", not "status would become X"). Say in words what a human must supply or decide; do not attach another status value to it. A separately labeled `Record state (not a status, not use-clearance): …` line is not a status. Nor is the comparison line `Packet says <packet status>; findings support <derived status>.` (TEH-RDY-063): it reports the packet's own status as an input beside the derived one; the `Status:` line carries the derived value. Checked by `scripts/check_single_status.py`.

## Finding rows (rules 2–4)

Apply precedence rule 1 first. Then take every **open** finding the skill wrote. The highest row that applies wins: `human_gate_required` > `revise` > `findings_only`.

| Status | Use it when (general rule) | Chair `decision` field |
|---|---|---|
| `human_gate_required` | At least one open finding cannot be closed by a copy change the chair can state from material in the packet — a human must judge or supply something. This covers: (a) a comparative, superiority or ranking claim with no basis in the supplied material (no head-to-head or other supplied comparative evidence), so only the sponsor can supply a basis or drop the claim; (b) authorization or approval status of the product or indication is unknown or not yet granted (pre-approval); (c) this chair disagrees with another chair on the same claim span; (d) a request to approve or clear, or to bypass any hard rule MLR-H1–MLR-H8 or other rule (precedence rule 1 — applies even with no finding and missing inputs); (e) an audience or channel gate only a human can settle — a genuine judgment call on supplied facts (for example the supplied audience or channel conflicts with the content, or the supplied facts support more than one reading). An audience, channel or rule pack that was simply not supplied is not row (e): it is a missing input (rule 4, `findings_only`; TEH-RDY-047). | `abstain` (chair cannot decide without a human) or `reject` when the chair finds the copy must not run in its current form. `mlr_validate_packet` then derives `human_gate_required`. |
| `revise` | Every open finding is correctable by a copy change the chair can state from supplied material: copy contradicts pasted label text (population, posology, indication wording) — or the person described such a mismatch, opened as a labeled description-based finding (TEH-RDY-035) — a mandatory element is missing and can be added, absolute or exaggerated wording (including absolute-language concerns under a national advertising rule set), a format element that can be added, a named source is cited but its locator is missing. A fail-close row stays fail-close — it is never waved through — but when the fix is clear from the supplied source, the status is `revise`, not a gate. | `revise` |
| `findings_only` | No open finding: observations only (severity `info`), or the chair could not assess because an input is missing (for example no label text pasted). Name each missing input as `[GAP]`; do not guess the finding. | as the packet requires — never presented as approval |

Which chair owns the finding (TEH-RDY-016):

- Ranking, superiority and "#1 / most effective" claims: Medical writes a finding only on clinical substantiation against supplied clinical data or label text. With none supplied, Medical records a `[GAP]` for the data, writes no medical severity, and routes the claim to Legal; Medical's status for it is `findings_only`. Row (a) above — the misleadingness of a claim with no supplied basis — is a Legal finding.
- Dose, posology, population, indication and clinical-outcome accuracy against the label: Medical owns it. Legal routes it to Medical and writes no legal verdict or severity on it.
- A claim routed to another chair is listed as a route, not as an open finding, on the routing chair's card.

Gate skills (TEH-RDY-022, TEH-RDY-058): when `mlr-channel-intent` (or any gate) returns `human_gate_required` on a judgment call on supplied facts (`status_basis: judgment`), including a channel / content mismatch (`channel_content_mismatch`), the packet status is `human_gate_required`. When the gate holds its decision only because inputs are missing or unmatched (`status_basis: missing_inputs` — no intent, a medium only, no posture), that is rule 4: the card shows `not classified — pending: <items>`, asks for each item, and the status is `findings_only`. A `treat_as_*` decision while a required input is still open is provisional: the card labels it `provisional — pending: <items>` and the status is `findings_only` — this includes a decision the gate reads from the supplied content when no intent was declared or the users are not decided (`provisional_label`, for example `provisional: treat as promotional — pending: who will use it`; TEH-RDY-062). A mixed promotional / medical-information piece is a judgment call (`mixed_content` in the gate result): `human_gate_required`, conflicting elements quoted (TEH-RDY-061). A `treat_as_*` decision with no open input is final and the status is `findings_only`. A card never shows a gated decision beside a lower status, and never shows a provisional decision without its label.

Rules that always apply:

- Fail-close is a property of a rule row, not a status (TEH-RDY-027). A fail-close row with a correctable copy or format fix is `revise`; it becomes `human_gate_required` only for rows (a)–(e) above.
- A missing input (no label text, no artefact text) is a `[GAP]`, not an open finding. A mismatch the person described is different: it may be an open finding, labeled `based on the person's description — verify against the artefact`, with the missing text as `[GAP]` beside it (MLR-H1 detail, TEH-RDY-035).
- Findings only on supplied issues (TEH-RDY-048): open a finding only on an issue present in the supplied text or described by the person. A hypothetical risk goes under a `Watch for:` note — no severity, no finding, no status change. A request naming only a category ("an omission") with no content is a missing input (`[GAP]`, rule 4).
- Severity alone does not set the status. A `critical` finding with a clear copy fix is `revise`; a `minor` finding that needs a human judgment is `human_gate_required`.
- Never lower a status to make the card look cleaner. When unsure between `revise` and `human_gate_required`, choose `human_gate_required` and say what the human must decide.
- Write the status on its own line, once: `Status: <value>`.
- Hard rules MLR-H1–H8 apply (see each chair's `SKILL.md`).
